입찰정보 서비스 개발계획서 검토 및 개선 권고사항

1.  종합 평가

전체적으로 계획서의 큰 방향은 적절하며, 바로 개발에 착수할 수 있을
정도로 구체화되어 있다.

특히 다음 사항은 긍정적이다. - 벤치마크 서비스를 그대로 복제하지 않고
공공데이터를 기반으로 신규 서비스를 구축하는 방향 - MVP와 유료 기능을
단계적으로 분리한 개발 계획 - 수집 로그 및 정정 공고 처리에 대한 고려 -
ASP.NET Core, PostgreSQL, Hangfire 등 비교적 안정적인 기술 스택 선정

다만 실제 개발 전에 데이터 수집 신뢰성, 법적 표현, MVP 범위, 운영 구조
측면에서 일부 보완하는 것을 권장한다.

2.  MVP 범위 축소 권고

현재 MVP에는 입찰 공고 자동 수집, 기초금액/A값/순공사원가, 개찰 결과,
회원가입·로그인, 구독 상태, 공고 검색·필터, 공고 상세, 관심
공고·폴더·휴지통, 투찰금액 계산기가 포함되어 있다.

개발자 1명 기준 9주 MVP 일정은 가능할 수 있으나 실제 나라장터 데이터의
예외 처리와 정정 공고 등을 고려하면 일정 위험이 있다.

추천하는 1차 MVP 범위: 공고 수집 → 검색/상세 → 관심 공고 → 투찰금액
계산기

회원 구독 상태, 결제, 고급 폴더, 경쟁사 분석, 알림 기능은 이후 단계로
분리하는 것을 권장한다. 특히 초기에는 공사·용역·물품을 모두 구현하기보다
‘공사’ 분야를 먼저 완성한 후 확장하는 방법을 추천한다.

3.  데이터 수집 주기 개선

현재 계획은 Hangfire를 이용하여 30분 주기로 나라장터 데이터를 수집하는
구조이다. 구조 자체에는 문제가 없으나 단순히 30분마다 신규 공고만
가져오는 방식으로 구현하면 운영 과정에서 누락이나 정정 공고 문제가
발생할 가능성이 있다.

추천 구조: - 5~10분 주기: 최근 변경 공고 증분 수집 - 30분~1시간 주기:
최근 24시간 데이터 재수집 - 매일 새벽: 최근 3~7일 공고 재검증 - 주 1회:
누락, 정정, 취소 공고 정합성 검사

즉 단순 주기 수집이 아니라 Incremental + Backfill 구조를 권장한다.

4.  공고 식별 및 변경 이력 관리

현재 Notice 테이블은 ’공고번호 + 차수’를 주요 식별 기준으로 계획하고
있다. 기본 방향은 적절하지만 실제 운영에서는 다음 정보를 함께 관리하는
것이 좋다.

-   원본 API 업무구분
-   공고번호
-   공고차수
-   재공고 여부
-   정정 여부
-   최종 수정일시
-   최초 수집일시
-   최종 확인일시
-   원본 응답 Hash
-   현재 유효 여부

특히 정정 공고 발생 시 기존 데이터를 단순 UPDATE하면 과거 상태를 확인할
수 없게 된다.

추천 테이블 구조: - Notice: 현재 공고 상태 - NoticeHistory: 공고 변경
이력 - CollectRaw: API 원문 데이터

5.  API 원문(Raw Data) 저장 권고

현재 데이터 모델에는 CollectLog가 있지만 API에서 받은 원본 데이터를
보관하는 구조가 명확하지 않다.

추천 테이블: ApiRawResponse - Id - ApiName - RequestParameter -
BusinessType - BidNumber - ResponseJson - HttpStatus - CollectedAt -
ParsedAt - ParseVersion

장점: - API 필드 변경 시 원본 확인 가능 - 파싱 오류 발생 시 재처리
가능 - API를 다시 호출하지 않고 데이터 복구 가능 - 데이터 누락 및 장애
원인 분석 가능

6.  나라장터 외 데이터 소스 확장 고려

장기적으로는 나라장터뿐 아니라 자체 전자조달 시스템을 사용하는 기관까지
고려할 필요가 있다.

예: - G2B 나라장터 - 국방전자조달(D2B) - 한국전력 전자조달 - LH 전자조달

처음부터 수집기를 인터페이스 형태로 설계하는 것을 추천한다.

IBidCollector - G2BCollector - D2BCollector - KepcoCollector -
LHCollector

초기에는 G2BCollector만 구현해도 된다. DB에도 SourceSystem 컬럼을
추가하여 G2B, D2B, KEPCO, LH 등 데이터 출처를 구분하는 것이 좋다.

7.  PostgreSQL 검색 구조

PostgreSQL 선택 자체는 적절하다. 초기 MVP에서는 PostgreSQL + pg_trgm +
ILIKE + 적절한 GIN Index 구성을 추천한다.

향후 공고가 수백만 건 이상 축적되고 검색 조건이 복잡해지면 OpenSearch
또는 Elasticsearch를 별도 검색엔진으로 추가하는 방법을 고려한다.

추천 전략: PostgreSQL로 MVP 구축 → 검색량과 데이터 증가 → 필요 시
OpenSearch 분리

8.  Blazor Server 선택 검토

현재 기술 스택은 ASP.NET Core (.NET 10) + Blazor Server이다. 기존 개발
자산과 개발자의 기술 숙련도를 활용할 수 있다는 장점이 있다.

다만 사용자가 증가할 경우 Blazor Server의 SignalR 연결 관리도 고려해야
한다.

선택안 A - 초기 개발 속도 우선 Blazor Server + ASP.NET Core

선택안 B - 장기 확장성 우선 ASP.NET Core Web API + Blazor WebAssembly
또는 React

장기적으로 사용자 증가와 외부 API 연동이 많아질 가능성이 높다면
프론트엔드와 API를 분리하는 B안을 검토할 가치가 있다.

9.  수집 워커와 웹 서버 분리

초기에는 VM 한 대에서 웹 서버와 수집 워커를 함께 실행할 수 있다. 그러나
프로젝트 구조는 처음부터 분리하는 것이 좋다.

예: - Bid.Web - Bid.Application - Bid.Domain - Bid.Infrastructure -
Bid.Collector.Worker

향후 Web Server, Collector Server, Notification Worker를 독립적으로
확장할 수 있다.

10. 개인정보 관련 표현 수정

계획서의 ’개인정보 국내 보관 요건 대응’이라는 표현은 개인정보가 반드시
국내 서버에만 저장되어야 한다는 의미로 해석될 가능성이 있다.

보다 정확한 표현: ‘개인정보 보호 및 국내 고객 대상 서비스의
운영·보안·컴플라이언스 관리 용이성’

실제 서비스 구축 시에는 개인정보의 수집, 이용, 보관, 파기 및 국외 이전
여부 등을 별도로 법률 검토해야 한다.

11. 정기결제 데이터 모델 강화

기술적인 데이터 모델에는 다음 항목을 추가하는 것을 추천한다.

-   구독 시작일
-   다음 결제일
-   자동결제 여부
-   결제금액
-   해지 예약
-   해지 완료일
-   환불 상태
-   PG 거래번호
-   PG Webhook 원문
-   결제 실패 횟수
-   마지막 결제 시도일

특히 PG Webhook은 반드시 서버에서 검증하고 원문 또는 처리 이력을 남기는
것이 좋다.

12. 추천 전체 시스템 구조

[외부 데이터] 나라장터 / 국방전자조달 / 한전 / LH ↓ [Collector Workers]
API 수집 / 재수집 / 정정공고 확인 / Raw JSON 저장 ↓ [Data Processing]
정규화 / 중복 제거 / 변경 이력 / 품질 검증 ↓ [PostgreSQL] Notice /
NoticeHistory / BidResult / Company / Member / MyBid / RawData /
CollectLog ↓ [Search Layer] 초기 PostgreSQL / 향후 OpenSearch ↓ [ASP.NET
Core API] 인증 / 검색 / 공고 / 계산 / 구독 / 알림 ↓ [Web] Blazor 또는
React / PC + Mobile ↓ [Workers] 메일 / 결제 Webhook / 마감 알림 / 개찰
알림

13. 우선 수정 권고사항

반드시 반영 권고: 1) API Raw 원문 저장 2) 정정/변경 이력 테이블 추가 3)
수집 재검증 및 Backfill 구조 4) SourceSystem 개념 추가 5) 개인정보 국내
보관 관련 표현 수정

강력 추천: 6) 초기 MVP는 ‘공사’ 분야부터 시작 7) Web과 Collector
프로젝트 분리 8) 초기 검색은 PostgreSQL 중심으로 구성하고 검색엔진은
필요 시 도입 9) 결제 Webhook 및 구독 상태 데이터 모델 강화

14. 최종 의견

현재 계획서는 개발 착수가 가능한 수준이다.

다만 9주 MVP를 성공시키기 위해서는 기능을 많이 구현하는 것보다 ’입찰
데이터가 누락 없이 정확하게 수집되고 변경 사항을 추적할 수 있는 구조’를
먼저 완성하는 것이 중요하다.

검색 화면이나 UI는 향후 비교적 쉽게 변경할 수 있지만, 초기 수집 구조와
데이터 모델이 잘못되면 서비스 운영 이후 전체 데이터베이스를 다시
설계해야 할 가능성이 높다.

권장 개발 순서: 1단계: 나라장터 실제 API 응답 분석 및 데이터 모델 확정
2단계: Raw Data 저장 + 공고 수집 + 변경 이력 + 누락 재수집 구조 완성
3단계: 검색 및 공고 상세 4단계: 관심 공고 + 투찰금액 계산기 5단계: 회원
구독 + 결제 + 알림 6단계: 경쟁사 분석 + 적격심사 + 외부 전자조달 시스템
확대

핵심 원칙: ‘화면보다 데이터를 먼저 안정화하고, 기능보다 수집 정확도를
먼저 확보한다.’
